PART 1 Project Purpose and Learning Targets
Build a Python Django application that lets campus users request equipment while administrators manage inventory,
approval, release, return, maintenance, and operational reports. The system must maintain an accurate history of each
physical unit and prevent equipment from being issued twice.

Work in groups of 5–6 members. Every member must contribute code, documentation, testing, and an individual
presentation segment. The instructor will announce the submission date; project presentation and Q&A occur in Week 17.

Exactly two user levels are permitted: BASIC USER and ADMIN. The admin side must be designed and coded by
your group using your own Django views, forms, templates, URLs, and ORM operations. Django authentication is
allowed; Django admin pages, admin.site.urls, and packages that generate the admin interface are prohibited.

Approximately three quarters of the required development work must focus on the custom admin side and one quarter on
the basic-user side. The admin side handles management, approval, operational workflows, reports, and settings; the basicuser side handles account access, browsing, requests, and tracking.

PART 2 Custom Admin Requirements
Provide dashboard, management, operations, reports, settings, and audit pages. Every protected server-side action must
enforce the admin role.

A1 Account management
List, search, activate, and deactivate basic-user accounts through custom pages. Show their request history. Deactivation
blocks new sign-ins and transactions without deleting existing records. Registration must never permit a user to select the
admin role.

A2 Equipment catalog and physical units
Create, view, update, and archive equipment categories and catalog items. Register physical units with unique asset codes,
condition, acquisition date, and status. Filter units by category, item, and status. Archive master records instead of deleting
records referenced by transactions.

A3 Request review and approval
Display a searchable, paginated queue filtered by status and date. Review item quantities, requested return date, purpose,
and current availability. Approve or reject with a recorded decision and reason. Allocate specific available units during
approval; an approved request reserves those units.

A4 Equipment release
Convert an approved request into an issued loan. Record the release date, releasing admin, assigned units, and due date.
Print a borrowing slip showing the borrower and asset codes. Prevent issuing a rejected, cancelled, already issued, or
insufficiently allocated request.

A5 Partial returns and overdue monitoring
Record returns per physical unit, including date and condition. Support partial returns; close the loan only when all issued
units are returned. Classify an outstanding loan as overdue when today is later than its due date. Put a damaged returned
unit into maintenance rather than immediately making it available.

A6 Maintenance and inventory reconciliation
Open and close maintenance records with problem, action, dates, and admin. Releasing a repaired unit makes it available;
retired units stay unavailable. Reject maintenance creation for a currently issued or reserved unit. Show derived available,
reserved, issued, maintenance, and retired counts that reconcile to physical-unit totals.

A7 Dashboard and reports
Provide four live cards: available units, pending requests, active loans, and overdue loans. Add a monthly issued-loan chart
and an equipment-category usage chart. Provide a date-filtered loan report and overdue report with CSV export. Derive
results from ORM queries and stored transactions.

A8 Audit history and operational settings
Record approval, rejection, cancellation, release, return, maintenance, account changes, and catalog changes with actor,
timestamp, action, and record reference. Provide a searchable admin-only audit page. Manage maximum loan duration and
maximum requested quantity; validate settings and apply them to new requests.

Dashboard values, charts, reports, and status indicators must change when database transactions change. Static
demonstration numbers do not satisfy these requirements

PART 3 Basic User Requirements
U1 Account and profile
Register, sign in, sign out, and edit only personal name/contact fields. Passwords must be handled by Django authentication.
Role and activation status are never editable by the user

U2 Browse equipment
Search active catalog items by name/category and view description, total serviceable units, and currently available quantity.
Hide borrower identities, internal notes, audit records, and maintenance details.

U3 Submit a borrowing request
Submit one request containing one to three different catalog items, quantities, purpose, and desired return date. Validate
positive quantities and duration limits. Submission creates a Pending request; it does not approve the request or reserve
units.

U4 Track and cancel own requests
View only own request/loan history, status, due dates, and released/returned units. Cancel only Pending or Approved
requests before issue. Cancellation of an Approved request frees its reserved units. Users cannot approve requests, release
equipment, record returns, or change due dates.

Shared sign-in and authentication infrastructure supports both roles; no third role such as staff, approver,
technician, or supervisor may be added.

Role and Access Rules
Use one authentication system with role-based redirects to /manage/ for admins and /portal/ for basic users. Users must
not self-promote through registration, profile fields, query strings, hidden inputs, or direct POST requests. Only an authorized
admin or a documented setup command may create another admin account

Scope every user record lookup by the signed-in owner. Protect detail pages, updates, cancellations, AJAX endpoints,
reports, and exports. Use active-account checks on protected actions so a deactivated user cannot continue submitting
transactions through an existing session.

Show explicit empty states, useful form errors, confirmation before irreversible workflow actions, and status labels that do
not depend only on color. Provide consistent navigation and responsive layouts for both sides.

PART 5 Business Rules and Technical Requirements
1. On approval, choose the required number of available physical units. Reserve all requested units atomically or
approve nothing. Release reservations when an approved request is cancelled.
2. An equipment unit has exactly one effective inventory status: Available, Reserved, Issued, Maintenance, or Retired.
Return and maintenance operations must maintain this invariant.
3. Use database transactions and a suitable locking or constraint strategy for allocation and issue. Demonstrate two
competing approvals for the last unit: only one succeeds.
4. Use a unique constraint for catalog item within a request. For a three-item request, validate every row before saving;
a failing row must not leave a partial request.
5. Default settings are a maximum of 7 calendar days and 3 units per request item. A requested due date must be
after submission and within the configured duration. Reject issue after the agreed due date; revise through a
recorded admin action before issue.
6. Compute overdue days as zero before/on the due date; otherwise use the calendar-day difference for each
outstanding loan. Payments, fines, procurement, and supplier portals are outside the required scope.

Required Django Implementation
Use Python and Django with Django ORM, migrations, server-rendered templates, template inheritance, URL names, forms
or ModelForms, and Django authentication. SQLite is acceptable for demonstration; PostgreSQL or MySQL may be used.
Choose a database appropriate to your concurrency strategy and explain its limitations.
Use one base template for each role and reusable components for navigation, forms, tables, and messages. Provide custom
list, detail, create, update, and archive operations where the workflow allows. Never allow unrestricted CRUD to bypass
transaction rules.
Use ORM relationships, filtering, ordering, pagination, and aggregate/annotate queries. Keep repeated business logic in
reusable functions, services, or model methods. At least one report must combine related models and computed totals.
Validate on the server. Protect state-changing forms with CSRF and use POST rather than GET for updates. Hash
passwords through Django authentication, escape user content, check object ownership, and keep secrets out of source
control.
HTML/CSS, JavaScript, Bootstrap styling, and a chart library are allowed. AJAX is optional. Third-party packages must be
declared and justified; they may not generate the required custom admin side.
Provide a requirements file with tested dependency versions, environment-variable guidance, migrations, seed setup, and
a README that starts the application on a clean machine. A working local demonstration is sufficient; paid hosting, external
integrations, and online deployment are not required.
